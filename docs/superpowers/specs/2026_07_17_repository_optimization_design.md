# 仓库第二轮优化设计

## 目标

在不改变现有 ASIN、1688 候选和 ROI 主数据流的前提下，提高计算参数的可追溯性、网络失败恢复能力、安装体验和 GitHub 维护效率。所有改动继续保留 Alpha/MVP 边界，不绕过 1688 登录、验证码或风控。

## 方案比较

### 方案 A：JSON 参数快照与轻量恢复（采用）

- 使用可选 JSON 文件覆盖内置 ROI 参数，未传配置时保持现有结果。
- 每次结果记录配置来源和完整参数快照。
- 对汇率与 MTop 的瞬时网络错误做有限重试。
- 采集过程中持续写入检查点，异常退出时保留已完成候选。
- 只增加标准库模块，不引入数据库或任务队列。

优点是可复现、兼容现有调用、测试成本可控，适合当前 MVP。

### 方案 B：全部改成 CLI 参数

实现最少，但参数数量多、命令难复用，结果文件无法可靠说明当时使用了哪组参数，因此不采用。

### 方案 C：数据库任务与断点续跑

恢复能力最强，但会引入任务状态、迁移和并发边界，明显超出当前单机工具的 MVP 范围，因此暂不采用。

## 组件边界

### ROI 参数

新增独立配置模块，负责默认值、JSON 读取、未知字段拒绝、有限数值与业务范围校验。`roi.py` 只消费已校验参数，不负责读取文件。

参数覆盖佣金率、单件仓储费、转化率、广告流量占比，以及重量和体积物流的四个单价。配置文件是可选项，默认值与当前版本完全一致。

### 可追溯输出

每个 `RoiResult` 保存参数来源和稳定排序的 JSON 快照。Excel 的 ROI、来源追溯和参数说明同步展示本次实际参数，避免自定义配置后仍显示固定口径。

### 网络恢复

新增通用 HTTP 重试边界，只重试传输错误、429 和 5xx。默认最多三次并使用短暂递增等待；认证失败、业务协议失败和普通 4xx 不重试。

### 采集检查点

`collect` 可接收检查点路径。每完成一个关键词就原子化更新候选 JSON；后续关键词失败时，已完成数据仍可用于人工排查和再次运行。Cookie 不进入日志、检查点或异常信息。

### 日志与错误提示

CLI 增加 `--verbose`，默认只输出警告和最终结果。错误 JSON 增加面向操作的 `hint`，但不输出 traceback 或凭证。GUI 继续复用 CLI 输出。

### GitHub 与安装

- CI 只在 `main` 推送和 PR 上执行，并取消同一 PR 的旧任务，避免一次分支更新触发两套重复矩阵。
- 增加 Windows 一键安装脚本、参数示例和发布检查清单。
- 更新仓库简介与 Topics，但不合并草稿 PR。

## 测试策略

- 配置：默认兼容、合法覆盖、未知字段、布尔值、非有限值和越界值。
- ROI：自定义参数实际改变结果，并保留来源与快照。
- 重试：瞬时失败后成功、达到上限、普通 4xx 不重试。
- 检查点：后续关键词失败时仍能读取前序候选。
- CLI：错误响应包含提示且不包含敏感 Cookie。
- 最终运行全量 pytest、Ruff、格式、隔离构建和 GitHub Actions。

## 明确不做

- 不自动获取 Amazon FBA、税费、退货率或实际物流报价。
- 不把搜索页最低价当正式采购价。
- 不自动解决 1688 验证码或风控。
- 不引入服务端、数据库、账号系统或定时任务。
- 不自动合并 `main`。
